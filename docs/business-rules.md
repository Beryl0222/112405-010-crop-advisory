# 业务规则与角色分工

本系统处理县级植保站收到的合成自然语言记录（农户短消息、技术员田间记录、农资标签摘录、检验结果等）。所有作物、药剂、病害、人员均为演练虚构，不构成真实诊疗或用药建议。

## 三角色工作流

系统内每个操作都校验经办人角色（`plantstation/roles.py`），越权调用直接抛出 `PermissionDenied`：

| 角色 | ID | 职责 | 对应模块 |
| --- | --- | --- | --- |
| 植保人员 | `U-STAFF` | 登记病害候选，判断田间观察现象与候选是否相符 | `candidates.py` |
| 农艺师 | `U-AGRO` | 起草/核对/批准防治建议，校验作物、施用时点、现场条件 | `recommendations.py` |
| 服务人员 | `U-SVC` | 决定是否向具体农户发送通知、登记执行、撤回未执行通知 | `notices.py` |

### 候选状态机（`CandidateStatus`）

```
candidate ──植保人员判相符──▶ matched（仍非确诊）
          └─植保人员判不符──▶ mismatched
candidate/matched/mismatched ──阴性检验──▶ ruled_out
                              └─阳性检验──▶ confirmed（确诊的唯一通道）
```

## 硬规则及其落位

1. **邻田经验不是本田证据。** 解析器对含"邻田、隔壁、转发、听说"等标记的整句或分句标 `is_hearsay=true, usable=false`（`parser.py`），候选登记与建议起草引用传闻证据时抛 `HearsayNotEvidence`。技术员记录中夹带的转述分句会被单独切出，不污染现场观察。
2. **符合性判断不是确诊。** 植保人员只能给出 `matched/mismatched`；`confirmed` 只能由阳性检验经 `apply_lab_result` 产生。
3. **阴性检验只排除目标病害。** 一条"未检出 D1"只把 D1 置为 `ruled_out`，D2 等其他候选状态不变，更不会被自动确诊；"不能证明 D2""未采样"类表述只存为说明性、不可用条目。
4. **标签限制逐字保留、不得被摘要省略。** 标签分句以原文存入 `label_clauses.text`，建议与通知只引用、不改写。溯源输出和校验报告都展示完整限制原文。
5. **标签放宽只对载明作物生效。** LABEL2 的"放宽"挂在 CR2 上；对 CR1 校验时该条仅作"不生效"提示，CR1 仍受"仅抽穗前、花期禁用"约束。
6. **施药建议的四项核对缺一不可**（`recommendations.validate_product_application`）：同田块非传闻可用证据；存在未排除且未判不符的候选；产品有适合作物的标签条款；当前生育期不在禁用期且未超出施用窗口。当前 T1 已由更正记录（CP-27）确认为开花期，施药建议必然被拦截并转 `rejected`。
7. **建议更新顶替未执行通知，已执行通知冻结。** 新批准建议发送时，同田块 `not_executed` 的旧通知置 `superseded`；`executed` 通知状态与 `basis_snapshot` 永久不变，撤回已执行通知会被拒绝。
8. **建议版本化。** `revise` 产生递增版本，旧建议置 `superseded` 但证据关联全部保留，通知快照可回溯当时依据。
9. **全程可溯源。** `provenance.py` 输出建议/通知依据的每条证据来源编号与原句、标签限制原文、候选状态依据，并单列被排除的传闻条目及其不可用原因——农户收到的不只是一个病名。

## 资料冲突与更正

资料陈述可以冲突，系统不按上传顺序推定效力：

- 生育期以"更正记录优先、否则取最新登记"解析（`repository.current_stage`）；
- 更正记录的作用范围按原文限定（CP-27 仅指 T1，T2 不被修改）；
- 同一作物下条款原文相同的标签限制只存一份，不同来源的同义限制（如"开花期不得施用"与"花期禁用"）各自保留，保证来源可追溯。

SQLite（标准库 `sqlite3`），建表语句见 `database.py`。运行期数据库默认在 `work/` 下，已在 `.gitignore` 忽略。
